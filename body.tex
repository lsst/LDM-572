\section{Introduction}

The Memorandum of Understanding with Chile \citedsp{Document-11622} roughly defines a Data Access Center (DAC) at the Base Facility in Chile.
In this document we would like to begin to specify more precisely what this Data Access Center would look like and the full range of services it will provide.
This should be seen as a discussion document to allow our Chilean colleagues to collaborate with us to define the Chilean DAC.

\section{The Chilean DAC}

Initially the thought was that the Chilean DAC should be very similar to the US DAC at SLAC.
However we now have a hybrid US DAC \cite{DMTN-287}.
It is unclear what the Google analogy would be in a Chile DAC,
We could deploy the Rubin  Science Platform (RSP) in Chile as the interface to the system,
but the google RSP will probably be more functional and more available.

It was considered more interesting to make the Chile DAC more a compute facility with HTCondor access to Data.

There was mention of interest in a copy or rapid access to the Prompt Product Database (PPDB).
That remains under development and was not originally considered for replication though there seems to be interest in that.

In 2026 a Chile DAC implementation committee was setup.
This committee will discuss and agree the various purchases for the Chile DAC.
In the first interactions an interesting in GPU was expressed.

The DAC will require  software, some  hardware, and of course data to function as a DAC.
We go through these in the following sections.

\subsection{Software and Services}
The Chile DAC will be administered  by Rubin's Chile DevOps team, any support from Chile community would be welcome as the DevOps team is under resourced (as of 2025).

\subsubsection{Accounts and Access }
Users will need a VPN to access the Chile DAC.
The 2026 purchase includes OpenVPN licenses for DAC users.
The VPN will require local accounts for each user with appropriate access controls via IPA.

During the FY26 purchasing cycle, we acquired licenses for 50 concurrent VPN users; however, the committee estimates actual concurrent usage will be closer to 20 users.

Since we have to create these accounts anyway granting access to the DAC with them will be more straight forward than
connecting to the Chile grid for authentication.
This will require lodging ssh keys with IPA and setting up 2FA.
We have discussed with the Chile community creating individual accounts for users there is no issue with this for now.

If we still wish to get the authentication system of the Chilean Grid integrated with the Chile DAC system \citedsp{LSE-279}
we will need to work with the Chile community.
There is a use case to  able to access Grid resources from the DAC using the same credentials, however users usually also know
how to use different credentials across systems fairly seamlessly.
This may be a heavy lift.

\subsubsection{Science Platform}
Deployment of the Science Platform in Chile is a potential overhead for maintenance to keep up with the Google deployment.
We may decide this is the correct approach but a conversation is need to make the tradeoff with RSP access on Google directly.
The Science Platform gives access, through the Notebook Aspect, to several versions of the LSST Software Stack allowing processing of image data and catalogs.
If the RSP is not deployed we would  have to handle local accounts in the DAC and provide container builds to run pipelines via e.g CernVMFS as is done in USDF.
This would be making the Chile DAC a batch access site as in \citeds{DMTN-223}

While users of the Chilean DAC will have access to the US DAC, \emph{user workspace data} is bound to the site where it was created.
Any data transfer would have to be done with e.g.  sftp.





\subsection{Hardware and infrastructure}\label{sec:hw}

The Chilean MOU provides for a DAC which is 10\% of the size of the US DAC.
The Data Release 2\footnote{Data Release 2 was used as a reference because the compute and storage resources required to support it were covered by the MREFC construction budget. Since the move to SLAC, this is no longer the case.} user computing resources at the US DAC are currently intended to comprise \citedsp{DMTN-135}:
\begin{itemize}
\item Computing: 2,400 cores ($\approx$ 18\,TFLOPs)
\item File storage: $\approx$ 4\,PB  (user file workspace: VOSpace or equivalent)
\item Database storage: $\approx$ 3\,PB (user database workspace)
\end{itemize}


Hence the Chilean DAC would at a minimum have:
\begin{itemize}
\item Computing: 240 cores ($\approx$ 1.8\,TFLOPs)
\item File storage: $\approx$ 400\,TB  (user file workspace: VOSpace or equivalent)
\item Database storage: $\approx$ 300\,TB (user database workspace)
\end{itemize}

This raises an immediate problem - 10\% of the data base is not very useful unless we bring only the Object catalog.
We shall discuss further in  \secref{sec:prop}.

In addition see \secref{sec:data}.
There will be additional computing capacity as required to support the operation of the Data Access services themselves as well as the Portal.

\subsubsection{Networks}

Access to the DAC will require network connectivity, and there are currently two possible ways to provide it.

The most direct option is to use the existing 10 Gbps Internet connection provided through NoirLab. This would require only minor network changes and could be made available relatively quickly, allowing DAC access to be enabled without depending on changes to the Rubin long-haul network (LHN).

A second option is to use capacity from the 40 Gbps backup link operated in coordination with REUNA. This could provide higher bandwidth for the Chilean community, but it would require more substantial network changes, including additional hardware such as a firewall, changes to the current routing configuration, and coordination with REUNA to enable and manage this traffic. 

The bandwidth available through this link would be managed using a priority scheme, with DAC traffic treated as one of several traffic classes. When higher-priority traffic is present, DAC traffic may be limited or queued. When capacity is available, DAC traffic would be transmitted on an “as available” basis. Implementing this option as part of the initial DAC deployment would therefore substantially delay its availability.

For this reason, the current approach is to provide DAC access through the 10 Gbps Internet connection, while continuing to evaluate and prepare the use of the 40 Gbps backup link as a future higher-bandwidth option, if this is the direction the community wishes to pursue.

\section{Conclusion}

We have started to put hardware in La Serena that will result in a useful scientific archive and data analysis service in the Base Facility in Chile.
This should enable local science activities and also provide seamless access to further resources at the USDF.
Discussion with the local community is on going and with the implementation committee in place as of 2025 we are in regular contact.
